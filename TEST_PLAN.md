# Тест-план: «Сквозняк»

Версия контракта: 0.1. Ответственный за смысл требований и приёмку — автор A, Ивчук М. П. Реализацию пишет D. Независимое ревью проводят B/C.

## 1. Цель и объект

Проверить соответствие будущего класса Skvoznyak и его исключений публичному контракту SPEC.md. Проверяемые входы, состояния и результаты описаны в TEST_CASES.md. Реальная аэродинамика и внутреннее устройство класса не проверяются.

## 2. Среда и данные

- Python 3.10+; только стандартная библиотека, unittest.
- Запуск из корня проекта; каталог tests является Python-пакетом.
- Эталон: Skvoznyak("Сквозняк", 200, 50), энергия 100, ветер 20, шесть исправных сложенных парусов, на земле.
- Каждое состояние создаётся через публичный конструктор и методы. Прямое изменение приватных полей запрещено.
- Каждый тест создаёт собственные объекты; порядок тест-методов не должен влиять на результат.
- Вещественные результаты — до 6 знаков, типы и логические результаты проверяются отдельно; принятие решения о допустимости операции — без допуска.

## 3. Область и методы

| Область | Подход | Кейсы |
|---|---|---|
| Конструктор и атрибуты | Классы эквивалентности, границы, типы, read-only | TC-01…TC-04, TC-09 |
| Подготовка, взлёт, посадка | Позитивные/негативные пути, повторные вызовы, точный бюджет | TC-05…TC-10 |
| Полёт и расчёт | Формулы, граница шторма, запрещённые среды, приоритет ошибок, атомарность | TC-11…TC-18 |
| Погода и повреждения | Переходы состояний и аварийная посадка | TC-19…TC-23 |
| Обслуживание | Допустимость на земле, запрет в воздухе, проверки аргументов | TC-24…TC-27 |
| Препятствия, снимки и ошибки | Матрица состояний, независимость словарей, иерархия | TC-28…TC-31 |
| Лимит маршрута | Достижение границы публичными действиями, порядок отказов | TC-32 |
| Последовательные истории | Given–When–Then через Pilot, Weather, Workshop | TC-33…TC-40 |

Каждый отказ метода проверяется сравнением публичных атрибутов до и после; конструктор при отказе не создаёт доступного объекта. Проверяется конкретный класс исключения, а не только наличие любой ошибки. Для NoEnergy проверяются required/available. Существование TC для требования не является доказательством покрытия всех возможных входов; новые найденные пробелы оформляются отдельными кейсами.

## 4. Этапы и команды

### До реализации

1. Проверить наличие документов, таблицу трассируемости и синтаксис тестов.
2. Выполнить команды ниже и сохранить факт ожидаемого отказа импорта.
3. Передать проект независимым ревьюерам B/C; автор отвечает на замечания в RESPONSES.md.
4. После согласования записать ссылку, участников, дату и версию заморозки.

```bash
python --version
python -m compileall -q tests
python -m unittest discover -s tests -t . -v
```

Сейчас реализация отсутствует: ожидается ModuleNotFoundError для skvoznyak. Отказ происходит при загрузке двух тестовых модулей; это **не 40 выполненных падающих кейсов**. Тесты не пропускаются искусственно и не используют фиктивную реализацию из поставки.

### После реализации

1. Зафиксировать коммит и версию Python.
2. Запустить модульные тесты, затем сценарные и полный набор:

```bash
python -m unittest tests.test_skvoznyak -v
python -m unittest tests.test_scenarios -v
python -m unittest discover -s tests -t . -v
```

3. По каждому падению записать TC-ID, ожидаемое и фактическое поведение, ссылку на SPEC, воспроизведение и классификацию: реализация / тест / ТЗ.
4. Согласовать и внести исправление. После изменения теста записать основание в CHANGELOG и добавить regression-тест с новым TC-ID. При существенном изменении замороженного ТЗ провести повторное ревью.
5. Повторить затронутые проверки и весь набор. Фактические результаты и решение — в ACCEPTANCE.md.

## 5. Критерии

**Вход в приёмку:** согласованное ТЗ, ответы на замечания, определённая версия, реализация в проверяемом коммите, доступный запуск.

**Выход из приёмки:** все 40 исходных тест-методов и добавленные regression-тесты прошли; нет failure, error, skip или expected failure; все подварианты subTest прошли; замечания закрыты или явно согласованно отложены; существенные изменения повторно рассмотрены B/C. Итог должен быть подтверждён фактическим логом, а не заявлением о готовности.

**Приостановка:** отсутствует реализация, не работает среда, обнаружено противоречие ТЗ/теста или несогласованная правка. Зафиксировать причину и продолжить после устранения; не ослаблять проверки ради зелёного результата.

## 6. Результаты и ограничения

Артефакты тестирования: TEST_CASES.md, tests/, лог конкретного прогона, записи об отклонениях в ACCEPTANCE.md, ответы в RESPONSES.md, изменения в CHANGELOG.md. Автоматическое измерение покрытия строк не заявляется: реализации ещё нет. Нагрузочное тестирование, безопасность среды исполнения, сеть и GUI вне области этой модели.
