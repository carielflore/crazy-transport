# Небесный парусник «Сквозняк»

Учебный проект по дисциплине «Сборка, тестирование и верификация программного продукта».

**Автор:** Ивчук Михаил Петрович, БСБО-16-23, №7.  
**Стихия:** воздух.  
**Этап:** ТЗ и приемочные тесты, версия 0.1, до заморозки.

![Сквозняк](docs/skvoznyak.png)

Одноместный небесный парусник с кольцом из шести складных парусов. Ловит ветер, летит быстрее в бурю, теряет несущую способность при повреждениях. Энергия нужна для взлета и управления; ветер удерживает аппарат в воздухе. Модель вымышленная, с детерминированными правилами.

## Состав

- [SPEC.md](SPEC.md) — назначение, конструкция, полный публичный контракт, сценарии, границы, исключения, трассируемость.
- [TEST_PLAN.md](TEST_PLAN.md) — область, методы, этапы и критерии тестирования.
- [TEST_CASES.md](TEST_CASES.md) — 40 кейсов: 32 модульных и 8 сценарных (80/20).
- `tests/test_skvoznyak.py` — модульные проверки по AAA.
- `tests/test_scenarios.py` — последовательные сценарии по GWT.
- `tests/helpers.py` — тестовые роли Pilot, Weather, Workshop и общие проверки.
- [RESPONSES.md](RESPONSES.md) — ответы на замечания ревьюеров.
- [CHANGELOG.md](CHANGELOG.md) — история изменений.
- [ACCEPTANCE.md](ACCEPTANCE.md) — порядок и протокол приемки.
- [DEMO.md](DEMO.md) — предварительный план совместной демонстрации с ожидаемыми результатами.
- [PRESENTATION.md](PRESENTATION.md) — предварительный план совместной защиты.
- [AUTHOR_CHECKLIST.md](AUTHOR_CHECKLIST.md) — проверка комплектности и незавершенные этапы.
- `docs/skvoznyak.png` — иллюстрация транспорта.

**Реализации `skvoznyak.py` здесь намеренно нет.** Ее пишет участник D на следующем этапе по контракту. Тестовые роли не входят в продукт и не содержат бизнес-логику.

## Запуск

Python 3.10 или новее. Только стандартная библиотека, установка пакетов не нужна.

Из корня проекта:

```bash
python -m unittest discover -s tests -t . -v
```

Отдельные группы:

```bash
python -m unittest tests.test_skvoznyak -v
python -m unittest tests.test_scenarios -v
```

До появления модуля реализации запуск заканчивается ошибкой импорта `skvoznyak`. Это ожидаемое состояние этапа ТЗ, а не успешное прохождение тестов. Не заменять импорт заглушкой и не отмечать тесты как skip/xfail ради зеленого результата.

Синтаксис файлов тестов можно проверить без реализации:

```bash
python -m compileall -q tests
```

## Что должен реализовать участник D

Добавить в корень `skvoznyak.py` с классом `Skvoznyak` и исключениями из SPEC, затем добиться прохождения всех 40 тест-методов, включая варианты subTest. Существующие тесты не ослабляются под реализацию. Неоднозначности сначала согласуются с автором ТЗ.

Тесты подготавливают состояния только через публичные методы; нельзя требовать определенных приватных полей. Изменение текста сообщения исключения не влияет на результат проверки. Сравнение вещественных результатов — до 6 знаков, а правила допуска операций — без скрытого округления.

## Порядок работы

1. Заполнить ссылку на репозиторий и роли B/C/D в SPEC по распределению преподавателя.
2. Ревьюеры добавляют отдельные файлы `REVIEW_...md` с замечаниями.
3. Автор отвечает в RESPONSES.md и синхронно исправляет SPEC, TEST_CASES и тесты.
4. После согласования установить дату заморозки и версию.
5. Участник D пишет реализацию; автор A ее не пишет. Вопросы и решения фиксируются в issue/PR, RESPONSES или CHANGELOG, а не остаются только в устной переписке.
6. Автор проводит приемку по TEST_PLAN и ACCEPTANCE. При падении сначала определяется источник: код, тест или ТЗ.
7. Каждая правка теста фиксируется в CHANGELOG и сопровождается regression-тестом с новым TC-ID. После заморозки существенные изменения ТЗ проходят повторное ревью B/C.
8. Автор и разработчик совместно завершают DEMO и PRESENTATION, вносят фактические результаты и выступают на защите. Авторская проверка комплектности не заменяет независимое ревью B/C.

При подготовке структуры использованы примеры:

- https://github.com/GurianovM/basalt_climber — контракт, таблица кейсов, тестовые роли, трассируемость.
- https://github.com/SurninDmitri/crazy-transport — разделение модульных и последовательных сценарных проверок.

Состав проекта адаптирован под этап ТЗ: дополнительные классы приложения, логирование и внутренняя реализация из примеров не переносятся автоматически.
